Récapitulatif complet – Incident du 2 mai 2026 (erreur HTTP 500 sur offipro.net)
Contexte
Le site offipro.net fonctionnait normalement le matin du 2 mai 2026.

Soudain, affichage d’une erreur HTTP 500 (Impossible de traiter la demande).

Les autres sites hébergés sur le même VPS (satpromax.com, skygros.com) restent accessibles.

Aucun git push ni modification des fichiers PHP/HTML n’a été effectué depuis plusieurs jours.

Aucune intervention humaine directe sur les configurations système du VPS.

Diagnostic initial
Les logs Nginx sont propres, mais le site ne répond pas.
En activant l’affichage des erreurs PHP dans index.php, on obtient :

text
Fatal error: Uncaught mysqli_sql_exception: No such file or directory in /var/www/offipro.net/connec.php:17
Le fichier testdb.php (créé pour tester la base) confirme :

text
Erreur BDD : SQLSTATE[HY000] [2002] No such file or directory
Conclusion : PHP ne peut pas se connecter à MariaDB. Le socket MariaDB n’existe pas car le service est arrêté.

Cause racine
MariaDB ne démarre pas. Analyse des logs (journalctl -u mariadb) :

Option de configuration invalide :
Ligne early-plugin-load = "" dans /etc/my.cnf (ligne 43). Cette option n’existe plus dans MariaDB 10.6.

Incompatibilité du répertoire de données :
La directive datadir = /www/server/data pointe vers un répertoire contenant un fichier ibdata1 au format MySQL 8.0 (incompatible avec MariaDB 10.6).
L’erreur remontée est :

text
InnoDB: MySQL-8.0 tablespace in /www/server/data/ibdata1
Données réelles ailleurs :
Les vraies bases de données actives (dont offipro_db) sont en réalité stockées dans /var/lib/mysql/offipro_db/ avec des fichiers datant du 1er mai 2026 (donc récents et intacts).
Mais MariaDB ne les voit pas car son datadir est mal configuré.

Origine probable (hors de ton contrôle)
Tu n’as touché à aucun fichier de configuration du serveur.
La panne est externe à ton code et probablement causée par :

Une mise à jour système automatique (Ubuntu) ayant modifié certains fichiers de configuration MariaDB.

Une intervention d’un outil de gestion tiers (aaPanel, phpMyAdmin) ayant réécrit /etc/my.cnf ou modifié le datadir.

Un redémarrage du serveur ayant réactivé une ancienne configuration incompatible.

Important : Ton changement d’environnement local (Windows → Linux Pop!_OS, XAMPP → Docker) n’a aucun lien avec cette panne. Aucun git push n’a été fait depuis ces modifications. Le problème est strictement côté serveur.

Actions correctives appliquées (2 mai 2026)
1. Commenter l’option early-plugin-load
bash
sed -i '43s/^/#/' /etc/my.cnf
Résultat : la ligne devient #early-plugin-load = ""

2. Changer le datadir vers le bon répertoire
bash
sed -i 's|^datadir =.*|datadir = /var/lib/mysql|' /etc/my.cnf
3. Corriger les autres chemins pointant vers /www/server/data
Édition manuelle du fichier /etc/my.cnf (avec nano) pour remplacer ou commenter :

slow-query-log-file=/www/server/data/mysql-slow.log → remplacé par
slow-query-log-file=/var/lib/mysql/mysql-slow.log

innodb_data_home_dir = /www/server/data → commenté (# en début de ligne)

innodb_log_group_home_dir = /www/server/data → commenté (# en début de ligne)

4. Redémarrer MariaDB
bash
systemctl start mariadb
Le service démarre sans erreur.

5. Vérification de la base de données
